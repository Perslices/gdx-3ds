# replays — canonical `.gdxrec` input recordings (input data, not game assets)

Format: `port/gdx_input_rec.h`. Stage with `tools/dev/oracle-run.sh --replay <name>` (copies to
sdmc `rec/<name>.gdxrec`, sets `[debug] input_replay=<name>`) or `gdx-dev emu run --replay`.

> **SHOT placement is DERIVED, not authored** (NEXT.md B15/B43, 2026-09-23,
> `docs/research/native/coverage2-progress.md`). A `SHOT` is the parity gate's sampler, and the
> gate can only see what a SHOT samples: the hand-placed schedules these files used to carry
> covered **49-80%** of what their replay actually draws, and five separate tracks were bitten
> by the gap (`explosions` hashed a deliberately wrong texture on all 640 explosions clean,
> `geomloss`'s machines truncation reached pixels and hashed clean at all 8 shots,
> `menus-longtail` hid a 41-frame divergence at 4145 between two shots 180 frames apart,
> `machfix`, `dropsites`). Every schedule below is now generated by
> `tools/dev/covsched.py derive --rewrite` from a `[debug] cov=1` coverage census of the
> replay, and covers **100%** of the distinct features the run touches. `src/*.gdxs` authors
> the INPUT only and emits no `shot` lines; regenerate a recording from it and then re-apply
> the schedule with `covsched.py`.
>
> **A derived schedule is a claim about replay CONTENT, so it is checked** (NEXT.md B48,
> `covfinish-progress.md`). Change a recording and its schedule stops covering it silently,
> while the gate goes on printing `divergent=0` over a shrinking sample. Two checks:
> `tools/ci-3ds.sh` runs `covsched.py lint` on every build (static, ~30 ms — a recording must
> carry a schedule, `src/*.gdxs` must author no `shot`, SHOT ticks must be on-stream, and no
> stretch may exceed the 300-tick floor), and `tools/dev/covdrift.sh` re-runs the census per
> release and asserts the committed schedule still reaches 100%. **If you re-record or extend
> any replay here, re-derive its schedule and re-gate it** — a new schedule is a new set of
> hashes.

> **The `Pins` column is descriptive, not prescriptive.** A `.gdxrec` header's `pins` line is a
> snapshot of the *recorder's* ini; the replayer prints it and applies nothing. Every file here
> says `renderthread=0` because of the SD the recording happened to run on, and that string was
> read back for months as if it were the gate's configuration — it never was
> (`docs/research/native/rtparity-progress.md`). **Both emulator lanes now default to
> `renderthread=1`**, the shipping mode (`kPipe` with `bridgemain=1`); `--ini
> debug.renderthread=0` is a deliberate bisect lever. Cite the run's own `[rt] mode=` receipt,
> which `fhdiff` prints for both logs and warns about when they differ.

## long-tail corpus (`replays`-track, 2026-09-20, build `native/replays@dd936b2`)

Authored with `tools/dev/mkgdxrec.py` from the step lists in `replays/src/*.gdxs` (regenerate
with `python3 tools/dev/mkgdxrec.py replays/src/X.gdxs replays/X.gdxrec`, then re-apply the
schedule with `tools/dev/covsched.py`). All four carry `det=1` pins and use SHOTs as the hash
sampler, because dense `fh_every=1` capture crashes the azahar-libretro core on the retro
lane's default renderer (verifymatrix-progress.md, lane finding 1) — a SHOT still emits a full
`[fh]` receipt, so N SHOTs give an N-point hash sequence for `fhdiff` at no idle cost. **Where
those N frames sit is the whole question**, and it is now answered by `covsched.py`, not by
hand.

## explosion corpus (`explosions`-track, schedule derived by `covfinish` 2026-09-23)

| File | Ticks / SHOTs | Reaches | Needs |
|---|---|---|---|
| `explosion-pileup.gdxrec` | 5700 / **50** | GP on the JACK cup (Mute City) driven into the wall and into the pack. TITLE → MAIN_MENU → COURSE_SELECT → MACHINE_SELECT → MACHINE_SETTINGS → GP_RACE, retire | — |

**A negative result kept on purpose, and now a measured one.** It was authored for a pile-up
and is not one (`explosions-progress.md` §5): 16 explosion sprites at `envmax=1`, never two in
one bracket, against the canonical replay's 640 at max 5. It therefore does **not** catch
`[native] fxceiling=3` — proven at `fh_every=1` over 1541 frames, `divergent=0`, with the lever
live — and no schedule can make it, because the lever reaches no pixels in this replay. That is
a replay-content problem, not a sampling one. The catch lives on `race-mutecity-start`
(`divergent=1 first_divergent=4268`). Its 39 hand-placed SHOTs covered **51.9%**, all of them
inside the race with the first 3300 ticks unsampled; the derived 50 cover 100%.
Authoring a *real* pile-up is now measurable rather than a guess: `covsched.py frames <cov.log>
fx:explosion` gives the sprite count and the frames, and the target to beat is `spr=16 envmax=1`.

`race-4p-vs` will not run without `[debug] pads=4` (`docs/3DS-HARDWARE.md`): the 3DS has one
pad and the decomp gates VS on the port count, so with the default `pads=1` the cursor never
lands on VS BATTLE and the replay walks a different menu.

Parity state per replay is in `docs/research/native/replays-progress.md` — two of the four
currently FAIL the `[native] all=1 interp=1` gate, with the lever bisected.

## residuals-track probes

Tick-exact truncations of `race-mutecity-start.gdxrec` (same header, same pins) with their own
`SHOT` sets. They exist because the RetroArch lane cannot afford `fh_every=N` (see
`docs/research/native/residuals-progress.md`, "Gotchas"): a `SHOT` still emits a full
`[fh] frame=… hash=…` receipt with `fh_every=0`, so a sampled hash sequence costs nothing
between shots.

| `probeboot.gdxrec` | 420 | 7 | fast boot/title check (~1 min/run) |
| `probetitle.gdxrec` | 1300 | 9 | 1300 ticks of ZERO input: stays on the title long enough for the audio-driven attract-demo trigger to be reached. Reproduces the boot residual pre-pin. |
